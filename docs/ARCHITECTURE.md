# System Architecture & Live Data Flow

This document details the end-to-end architecture and operational data flow of **Job Scout**. All endpoint definitions below are automatically inspected directly from the FastAPI application (`backend/app/main.py`).

## 2. Architectural Pillars

### A. Privacy-First & 100% Offline Operation
- **Offline Mode**: Backend and scraper containers run with `HF_HUB_OFFLINE=1` and `TRANSFORMERS_OFFLINE=1`. Models (`all-MiniLM-L6-v2`, `unsloth/Llama-3.2-3B-Instruct`, and `TinyLlama-1.1B-Chat-v1.0`) are pre-cached in `./models`.
- **Zero External Egress**: No candidate resumes or job descriptions are transmitted to third-party AI APIs (OpenAI, Anthropic, Google). All inference occurs on host hardware.

### B. Embedding Dimension Integrity
- **Native 384-d**: Embeddings generated by `all-MiniLM-L6-v2` are stored as native 384-dimensional vectors (`Vector(384)`) in PostgreSQL via `pgvector`.
- **No Zero-Padding**: Vectors are stored without artificial zero-padding, preserving cosine angle geometry and optimizing disk footprint.

### C. Hybrid Search Formula
The hybrid retrieval engine evaluates candidate-to-job fit via a linear combination of vector semantic closeness and exact keyword occurrence:

$$\text{Score} = 100 \times \left(0.7 \times (1 - \text{cosine\_distance}) + 0.3 \times \text{keyword\_score}\right)$$

Where:
- $\text{cosine\_distance} = \mathbf{u} \cdot \mathbf{j} / (\|\mathbf{u}\| \|\mathbf{j}\|)$ via `j.embedding <=> :embedding`
- $\text{keyword\_score} = \frac{\sum \text{CASE WHEN title MATCH THEN 2.0 WHEN desc MATCH THEN 1.0 ELSE 0.0 END}}{2.0 \times n_{\text{skills}}}$
- Alphanumeric skills use PostgreSQL word-boundary regex (`\y<skill>\y`).
- Special character skills (e.g., `C++`, `C#`, `.NET`) use substring matching (`LIKE`).

### D. Plain-Text Chunked HTTP Streaming
- Generation endpoints (`/ai/generate`, `/ai/refine`, `/ai/research`) utilize FastAPI's `StreamingResponse` with `media_type="text/plain"`.
- Tokens are pushed over standard HTTP chunked transfer encoding, enabling real-time token rendering on the frontend without Server-Sent Events (SSE) event framing overhead.

## 4. Containerized Microservices

The application is orchestrated via six Docker services defined in `docker-compose.yml`:
1. `db`: PostgreSQL 15 + `pgvector` on host port `5435` with HNSW indexing.
2. `redis`: Redis cache & Celery message broker on host port `6380`.
3. `backend`: FastAPI application server on host port `8001`.
4. `scraper`: Celery worker executing multi-portal scraping and embedding pipelines.
5. `celery-beat`: Periodic scheduler triggering job scraping cycles every 10 minutes (600s).
6. `frontend`: Next.js 16 (React 19) web application on host port `3000`.
